# 17 — Undo and Action History (NEW)

Directive from Matt (2026-08-15): *"i would like to undo the previous action (previous move, previous sort)"*

Two layers hide in that one sentence and must never be confused. A **move** changed the vault and is recorded in the corpus (12 §2); a **sort** changed only what the right pane was showing and was never recorded at all. This doc specifies both: a core-owned, recorded, refusable **vault undo**, and a client-local **view undo** — presented to Matt as one `u` key, with a toast that always names which layer it just touched. Doc 05 §8 said "No automated undo command is in scope"; **this doc supersedes that sentence** and keeps everything else in 05 §8 (the operation log and backups remain the manual reversal path, and `undo_info()` is unchanged — automated undo cannot key off it, because a log line carries no action id and no content hashes).

The governing fear, stated once: **an undo that half-works is worse than no undo.** Every rule below exists to make partial application impossible or, where it is genuinely possible, loudly recorded.

## 1. What is undoable

"Undoable" means the core can return the vault to byte-identical pre-action state using only the sanctioned primitives of 05 §1. Anything less is named honestly.

| Action (`ActionRecord.operation`) | Undoable? | What undo does, exactly |
|---|---|---|
| `move` | **Yes, fully** | **Retire first, restore second:** archive the organized copy, *then* verified-relocate the archived original back to its capture path. The order is load-bearing, not incidental — see the crash-interim invariant below the table. The pre-move frontmatter comes back for free: 05 §2 step 6 wrote the tag / `processing_status` / `last_edited_date` onto the **copy**, never onto the archived original. |
| `archive` | **Yes, fully** | Verified relocate from the archive path back to the original path. |
| `skip` | **Yes**, in two halves | It touched no file and wrote no oplog line — only an ActionRecord. Undo appends an inverse record so the counterfactual corpus stays honest (`op.skip` exists precisely to preserve that counterfactual), and, **if the originating session is still alive**, puts the capture back in front of Matt (§7). A skip from a dead session undoes its corpus half only, and says so. |
| `meta_edit` / `tag_edit` | **Yes, fully** | A **key-scoped** frontmatter write restoring `capture.frontmatter_before` for exactly the keys that changed — `keys = { k : capture.frontmatter_before.get(k) != capture.frontmatter_after.get(k) }`, **derived from the record at undo time**, never read from an operation payload. Both fields are on `CaptureState` (`actions.py:151,153`) and both are persisted, so the derivation needs no new schema. A record whose `frontmatter_after` is null is **not** a `meta_edit`/`tag_edit` and refuses (§3). The write goes through `update_frontmatter(..., replace_keys=<those keys>)` so a list field is replaced, not appended. **Per-key value-scoped precondition:** undo proceeds only where `current_frontmatter[k] == capture.frontmatter_after[k]` for every derived key; any drifted key refuses the **whole** action (§3). It does **not** restore the file from the backup and it does **not** hash the body — the left pane is a live editable buffer (10 §4) and Matt may have legitimately edited the body since; blowing that away to reverse a tag would be the data loss this doc exists to prevent. Not hashing the body is exactly what the per-key value check pays for: without it, the auto-tagger (doc 06/11, a separate systemd process) adds a tag between the edit and the undo and `replace_keys` silently deletes it — no refusal, no toast, no record. |
| `merge` | **Partially** — restore-or-refuse | Two things happened: the target was rewritten (backed up) and the capture was archived. Undo restores the target's pre-merge bytes **and only when the target's current bytes still hash to the record's `targets[].after_hash`**, then restores the capture from the archive. **Restore source, in order:** `targets[].before_text` (`actions.py:196` — it exists, it is *on the record*, and it needs no side file), falling back to `context.backup_path` (invariant 6). The current target is itself backed up **before** being overwritten, uniformly with 05 §1.4. If the target changed since, undo **refuses**. It never attempts a three-way merge. Merge is **not undoable at all** only when *neither* source exists — the target exceeded the `before_text` capture ceiling (64 KB) **and** no backup was taken. With `file_ops.create_backups = false` that is every merge over 64 KB, and `organize health` must warn about it, because the config silently costs a safety net. |
| `append` (tag-route, 11 §1) | **Partially** — two tiers, then refuse | Tier 1 (`restore`): target still hashes to `after_hash` ⇒ restore the pre-append bytes byte-exact, from the same source order as `merge` (`targets[].before_text`, then `context.backup_path`). Tier 2 (`excise`, `undo.append_strategy = "restore_or_excise"`): the target changed elsewhere, but the recorded appended block **and** its machine-owned `append_marker` (CRITICAL-1) still appear verbatim exactly once ⇒ remove exactly those bytes, backup first, atomic write. Tier 3: neither holds ⇒ **refuse**. Note the append did *not* archive the capture — the route layer archives separately as its own record with its own undo. **The pipeline half:** after an append undo, the doc-06 delivery-store row for that capture is rewound **in the same undo** when the store is reachable; when it is not, the divergence is recorded in `context.partial_failure` naming the store. Without this the appended block is gone from the target while the store still says *delivered*, so it is never re-delivered and no record says so. |
| `integrate` commit | **Partially** — restore-or-refuse | Identical rule to `merge`, including the restore-source order (`targets[].before_text`, then `context.backup_path`) and the back-up-before-overwrite step: restore the pre-integrate bytes iff the target still hashes to `after_hash`, else refuse. The LLM is **never** re-run. |
| `create_folder` | **No** | Removing a directory is a delete, forbidden by 05 §1.1, and nothing durable can even tell whether the folder pre-existed — no `ActionRecord` field carries it and no oplog line carries it. Undo refuses and names `rmdir` as the manual step. If `ui.auto_move_to_new_folder` fired a move into it, **that move is a separate record and is undoable** — undo it and the folder is left empty but harmless. |
| any `consumer:*` action (taskwarrior, anki/learn, question_answer, deep_research) | **No** for the foreign half; **yes** for the vault half | The consumer wrote into a system this core does not own (`~/.task`, Anki) and cannot transactionally revert. **The discriminator is computable from existing data and needs no new schema field:** a `consumer:*` record is undoable **iff** its `operation` is `meta_edit` or `tag_edit` — the vault-side write-back (`actor: consumer:learn`), an ordinary key-scoped metadata undo. **Every other operation by a `consumer:*` actor refuses**, naming the external system and the consumer's own backup dir. |
| `auto-organize` application (13 §2 `auto_below`) | **Yes** — whatever it did underneath | It is a move/append/integrate and undoes by those rules. It also carries the strongest calibration signal doc 13 has (§4). |
| `op.merge_preview` | **Nothing to undo** | It is in `MUTATING_METHODS` for lock discipline only; it writes no file and emits no record. |
| a **view** change (sort cycle, selection, browse descent, search, pane focus) | **Yes**, client-locally | Never recorded, never an RPC. §7. |

**Crash-interim invariant for the move undo (why retire-first).** The two steps cannot be one atomic act, so the only question is which interim state a crash may leave. Retire-first leaves the note **only in the archive**: recoverable by hand, no live duplicate, and — decisively — no window in which a live capture at `capture/raw_capture/…` with `processing_status: raw` coexists with a live organized copy sharing its `id` and `aliases`. Restore-first opens exactly that window, and the doc-06 pipeline scans the capture folder every 10 minutes: it would re-consume the capture and produce a duplicate Taskwarrior task, a duplicate flashcard and a second route append. Pinned by a kill-between-steps test (§8). The same ordering is why acceptance test 1's archive path carries a collision suffix — the archive slot is written first, while the original is still archived.

## 2. The undo model

**Decision: an undo is a NEW forward operation, not a rollback.** It is executed through the ordinary `fileops` context, writes its own operation-log lines, appends its own `ActionRecord`, and is itself undoable — undoing an undo *is* redo, and the chain is visible in history.

Justification against the never-delete law: a rollback wants to move files backwards (`os.replace`/`rename`) and to amend history. Both are structurally forbidden here — the AST guard in `tests/test_fileops_safety.py` names the only three functions that may remove a path, and the corpus is strictly append-only (`_append_line`, cross-process lock, torn-tail healing). A forward inverse needs neither: every restore is `atomic_write` or a verified relocate into a free path, so **at no instant is a byte of note content absent** — with `atomic_write` the old bytes are readable until the rename and the new bytes after it; with a verified relocate the note is at the old path or the new one, never neither. (The stronger claim "never in only one place" is *false* for the relocate path — a rename leaves exactly one copy — and must not be made; the property that actually holds, and the only one undo needs, is **atomicity**.) The corpus, meanwhile, only ever grows.

Resulting invariants:

1. **Precondition-complete before the first write.** Every precondition of §3 is evaluated against the whole action — every target of a multi-destination route batch included — before anything is touched, **and a `FileSnapshot` is taken per touched file at that moment**. The window between evaluation and write is not empty, so `fileops.check_unmodified` runs **immediately before each individual write** (the house TOCTOU rule, `fileops.py:872-880`). A failure *there* is invariant-3 territory — `ok=false` plus `context.partial_failure` naming the file — and never a silent clobber; it is not a §3 refusal, because by then something may already have been written. A batch is all-or-nothing **at the precondition stage**: one failing target refuses the whole undo before any write happens.
2. **Undo never merges, never guesses, never partially applies by design.** It restores exactly, or it refuses.
3. **If it fails mid-flight anyway** (disk full after restoring target 1 of 2), it returns `ok=false`, writes `[FAILED]` oplog lines, and sets `context.partial_failure` on its own record naming exactly what did not finish. **A partially-applied undo does NOT mark the original as undone** (§5) — the original's effect is still partly present, so calling it undone would be a lie the learner would act on.
4. **Operation log**: one line per file the undo actually moved or rewrote, type `undo`, ordinary grammar `[<ts>] undo: <src> -> <dst> [SUCCESS|FAILED][ Backup: …]`. This **extends 05's closed line-type list** (`move|archive|merge|create_folder|metadata`) by one value — the only line of 05 this doc changes besides the §8 sentence named in the header. The single-line grammar and its escape table are **not extended**: "this undid act_X" lives in the corpus. **The oplog↔corpus join is specified, not assumed**, because undo's ability to find an archive or backup path for a pre-v2 record depends on it entirely: match on (line type ∈ {`move`, `archive`, `merge`, `metadata`}, `src` **or** `dst` equal to a record path, and `ts` within ±2 s of the record's `ts` — both sides stamp at second granularity from the same `now`); on multiple matches take the exact path-pair match; on remaining ambiguity **refuse** — `UndoRefused: cannot identify the backup for act_01J… (ambiguous oplog join)`.
5. **Corpus**: exactly one inverse `ActionRecord` per undo, carrying the full `targets[]` before/after of the reversal. `operation = "undo"` — a new value in both `fileops.OperationType` and `actions.Operation`, plus `_ACTION_OPERATION["undo"] = "undo"`. This **extends 12 §2's closed operation enum** by one value; every other line of 12 §2 stands. **`ACTIONS_SCHEMA_VERSION` becomes 2** — not because old readers reject unknown operations (they do not), but because a v2 *writer* emits an `operation` value that a v2 reader must accept **strictly**. Forward compatibility for v1 readers is already provided by the relax rule at `actions.py:500-510` (`strict = version <= ACTIONS_SCHEMA_VERSION`), which is precisely why no existing reader breaks; the bump is a writer-side declaration (§4 migration). `tests/test_actions.py`'s literal `== 1` is updated in the same change. No existing line is ever rewritten.
6. **The oplog is not the undo input.** `op.undo` keys off the `ActionRecord`, which carries `id`, `capture.content_hash`, `capture.frontmatter_before` / `frontmatter_after`, and `targets[].before_hash` / `after_hash` / `before_text`. **`ActionContext` additionally gains `backup_path: str | None`** — trailing, defaulted, omitted from `to_json()` when empty, parsed fail-closed, exactly the `dry_run` / `partial_failure` promotion shape — because sourcing the backup from the log is not sound: `file_ops.log_operations` defaults true but is settable false (`config.py:160`), and glob-guessing among `backup_file`'s `_1`/`_2` collision names silently restores the wrong content. The invariant-4 join is the **fallback for pre-v2 records only**.

## 3. Preconditions and refusals

**Decision (⚠ narrowed deviation from the "where the error line falls" ruling, deliberate and granted):** every undo *refusal* raises `-32000` with a discriminable `error.data.kind` and writes **no oplog line and no ActionRecord** — nothing happened. `ok=false` is reserved for an undo that began and could not finish (invariant 3).

**The deviation is two rows wide, not sixteen.** `ConcurrentModificationError` is already on the RAISE side of `ARCHITECTURE.md:445` and is therefore no deviation at all; nor is any row whose reason is addressing (no such id, wrong operation type, disabled feature, actor rule). The genuine deviation is the two **world-state** rows — *the archived original is missing* and *no restore source exists* — which raise rather than returning `ok=false` with a `[FAILED]` oplog line. That narrowed deviation is **granted**, on the ground that an undo refusal is always a *precondition* failure evaluated before any write, so it is structurally an addressing failure even when the reason is world state, and recording a `[FAILED]` line for an attempt that touched nothing would pollute the one log whose purpose is manual reversibility. **The grant is written into `ARCHITECTURE.md` in the same change** (that file is architect-owned; this doc's seat submits the edit) — a shared-file ruling that lives only in a spec doc is how the two records drift.

One new error class, `UndoRefused(OperationError)`, exists so the client can branch on `error.data.kind` for its toast (the standing ruling: a client MUST check `result.ok` **and** branch on `error.data.kind`). Everything else reuses the existing taxonomy. User-facing shape is the house one-liner — `<ClassName>: <message>` then `hint: <hint>`, never a traceback.

| Precondition violated | Class / `data.kind` | Message shape |
|---|---|---|
| No such action id | `OperationError` | `OperationError: no action act_01J… in the corpus (scanned 2 month files)` · hint: `organize actions history --limit 20` |
| Already undone | `UndoRefused` | `UndoRefused: act_01J… was already undone by act_01K… at 2026-08-16T09:12:04Z` · hint: `undo that one to redo this action` |
| Operation type not undoable | `UndoRefused` | `UndoRefused: create_folder is not undoable — removing a directory would be a delete (spec 05 §1.1)` · hint: `rmdir <path>` by hand |
| Foreign-system effect | `UndoRefused` | `UndoRefused: consumer:taskwarrior wrote outside the vault (~/.task); organize cannot revert it` · hint names the consumer's backup dir |
| A touched file changed since the action | `ConcurrentModificationError` | `ConcurrentModificationError: areas/health/training-log.md changed since act_01J… (sha256 3f9c… != a71b…)` · hint: `inspect the file; undo will not overwrite later edits` |

| The oplog join is ambiguous (pre-v2 records only, invariant 4) | `UndoRefused` | `UndoRefused: cannot identify the backup for act_01J… (ambiguous oplog join)` |

A concurrent **server** writer is not a refusal: `op.undo` is in `MUTATING_METHODS` and waits its turn in the `WriterQueue` under the write lock, like every other mutating call. But the queue serialises **server clients only**. It bounds neither the doc-06 automation pipeline (a separate systemd process writing the same vault every 10 minutes) nor a CLI-side `organize undo` run outside the server. Those two are why invariant 1's per-write `check_unmodified` exists and why the changed-file rows above are operational rather than theoretical.

## 4. Learning interaction

The undone action's teaching must go away, and the code cannot subtract it: `learning.json` is a lossy derived view with **no provenance** — `last_used`/`last_seen` are clobbered scalars, `total_moves` is a global denominator, and `apply_decay` may already have hard-deleted the association. So: **mark the corpus, then rebuild the view.** `learn.py` already declares the right hierarchy — "the action log is the source of truth, `learning.json` is a derived view".

**Representation — inverse record plus one correlation field.** `ActionContext` gains `undoes: str | None`, the `act_<ulid>` of the reverted action, on the **inverse** record. Trailing, defaulted, omitted from `to_json()` when empty, parsed **fail-closed** — exactly the shape of `LLMTrace.proposal_id` / `stale_target` and of the `dry_run` / `partial_failure` promotions. Rejected alternatives, and why: an *excluded flag mutated onto the original line* would require update-in-place on an append-only file whose locking is designed only for appends; a *pure tombstone* would be a second record for one event when the undo already changes the vault and must record anyway.

**What each reader must do:**

| Reader | Change |
|---|---|
| `learn.record_action` | Skip the **inverse** (one guard beside the `partial_failure` gate: `context.undoes is not None` ⇒ `None`) — the folder the note lands back in is usually the inbox, and teaching "captures like this belong in the inbox" is actively wrong. On replay, also skip any record in the undone set. |
| `learning.json` | **Rebuilt, not decremented — and deferred, computed off-lock.** Replay `ActionRecorder.query()` oldest-first through `record_action` with the undone set excluded, applying decay at each record's **own** `ts` so the rebuild is a pure function of (corpus, config). ⚠ This makes `learning.json` reproducible and testable, which the incremental path never was; it is a deliberate behavior change. **It cannot run in band.** Every mutating method runs inside `writer.submit` under `_rwlock.write()` (`server.py:1241-1248`) while `suggest.for_note` takes `_rwlock.read()`; a ~940 ms replay held there would blow the 50 ms budget *and* block every reader. So `op.undo` **marks the corpus, queues the rebuild, and returns** with `learning: { "rebuilt": "scheduled" }`. The rebuild then computes a new learning object **outside** the rwlock — it is a pure function of (corpus, config) and needs no lock to compute — and takes the write lock only for the final swap and `learn.save`. **`learning.json` is snapshotted into `<backup_dir>/` before every rebuild**, which is what discharges 14 §7's "any format change backs up first" for a wholesale replace. On the server the swap replaces `self._learning` — 🔴 the server caches learning and never re-reads it, so it must additionally reload from disk whenever the file's mtime changed since load, or a CLI-side undo is silently overwritten. `organize health` reports learning as **stale** from the moment of the mark until the swap lands. Gated by `undo.rebuild_learning` (default `true`); when false the corpus is still marked, nothing is queued, and `organize health` reports learning as stale-by-N-undos. The rebuild's own result — `{ records_replayed, duration_ms, destinations_before, destinations_after, evicted: [...] }` — is reported by `organize learn rebuild --json` and the learn-rebuild path, **not** by `op.undo`. |
| `ActionRecorder.query_similar` | **Highest severity.** Exclude undone originals — doc 13's precedent retrieval would otherwise re-propose exactly the thing Matt just reverted. |
| `ActionRecorder.stats` | Undone records stay in `total`, `by_operation`, `by_actor`, `by_route`. **They are also RETAINED in the denominator of `with_suggestions`, `top_accept_rate`, `rank_histogram` and the `integrate.*` verdict rates** — and when the **undo's actor is not human**, the undone accept additionally counts as a **negative** in the numerator's complement. New counter `undone: N` beside `partial_failures`. The earlier adjudication (*"an undone rank-1 accept is dropped, not counted against the engine, because a corrective action normally follows"*) is **struck**: it is an assumption about human behaviour, not a guard. Dropping it produces a self-reinforcing loop — auto-organize applies below threshold, the application is wrong, a machine undoes it, the failed rank-1 accept leaves the denominator, and the very fraction the trust ladder calibrates on **rises** after each failure. Retention plus the machine-undo negative makes the arithmetic point the right way; the §3 refusal that a machine may only undo its own work is what stops a machine from manufacturing negatives against someone else's actions. |
| `ActionRecorder.query` / `export` | **No change.** Both lines are the audit trail and must survive. Exclusion belongs to precedent readers, not to the stream. |

**Firewall proof (Phase-6 ruling: `LLM_EDIT_ACTORS` stays `frozenset({"claude-integrate"})`).** Three steps. (i) The inverse record's actor is whoever performed the undo, and it passes through the human-decided predicate unchanged, so a machine-initiated rollback folds nothing — undo requires **zero** widening of `LLM_EDIT_ACTORS`. (ii) Undo introduces **no decrement primitive**: the only write to `learning.json` remains a full rebuild that replays through `record_action`, which already gates on that same predicate. Excluding an undone record can therefore only remove *that record's own* contribution, and only if it was foldable in the first place. (iii) The remaining hole — a machine erasing the owner's learned preferences by undoing their actions — is closed by the refusal in §3: **a machine actor may not undo a human-decided action**, and may not undo any action it did not itself perform in the same run. That rule is deliberately not a config key; making it configurable would re-open the exact one-directional firewall the Phase-6 ruling protects. Corollary, stated precisely so it issues no directive to the unexecuted Phase-6 ruling: **undo READS `applied_via` when deciding whether an action was human-decided, and records the undo's actor in the inverse record's own `actor`.** They are two different facts — `applied_via` is a property of how the *original* edit reached the file, while "who undid it" is the actor of the *inverse* record, which `ActionRecord.actor` already carries — and fusing them would make the Phase-6 gate read a field with two meanings. This document requires no change to the Phase-6 design.

*(Doc 14's de-Matt-ification governs the spelling, and doc 14 **owns the rename**: its work-list row A6 renames `is_matt_decided` → `is_human_decided` across its eight call sites, carrying this firewall note with it. This document therefore names no identifier that contains a person's name: the normative predicate is `fileops.is_human_actor` — the `human:*` namespace plus the configured `[identity] actor` — and the no-AI rule keys off `[safety] no_ai_key`. The semantics are the vault owner's identity, whoever that is.)*

**Migration / compat.** No record on disk is ever rewritten. `context.undoes` and `context.backup_path` absent ⇒ `None` (fail-closed), so every pre-existing record reads back as "not an undo" with no recorded backup, and no pre-existing record is in any undone set. `ACTIONS_SCHEMA_VERSION` becomes `2` as a **writer-side declaration** (invariant 5) — a v2 writer emits a new `operation` value that a v2 reader must accept strictly; readers accept `schema_version <= 2` and the `actions.py:500-510` relax rule already keeps v1 lines readable, so nothing on disk breaks. A v1 corpus is undoable — v1 records carry `content_hash`, `before_hash`/`after_hash`/`before_text`, and the invariant-4 oplog join supplies the backup/archive path, refusing only when that join is ambiguous.

## 5. Depth, chains, redo, and history

**Undo is addressed, not stacked.** There is no depth limit and no "must undo in order" rule: any action in the corpus may be undone at any time, because safety comes from the §3 preconditions (which check the *current* state of every touched file), not from adjacency. A twenty-step-old move whose files nobody has touched is exactly as safe to undo as the last one; the action before it whose target was edited yesterday is refused, whether it is one step back or fifty. Age is therefore not a gate by default: `undo.max_age_days = 0`, and **`0` means no age limit** (TOML has no null, so `0` is the single spelling — see §6). The gate, when enabled, is exactly `max_age_days > 0 and age_days > max_age_days`. The corpus **scan** window is bounded for performance only (`undo.scan_months`, default `2`).

**Undone-set definition** (well-founded; every candidate `Y` is strictly later in the corpus than `X`, and the chain is finite):

> `undone(X)` ⇔ ∃ a record `Y` with `Y.context.undoes == X.id`, `Y.context.partial_failure is None`, and `undone(Y)` false.

So A-undone-by-B ⇒ A is undone; B-undone-by-C ⇒ B is not in effect ⇒ A is in effect again. **There is no separate redo verb in the core**: redo is `op.undo` addressed at the inverse record. The client binds `U` to that (§7) so Matt never types an id.

**The history view** lists, newest first, one row per record in the scan window: `ts` (relative — "4m ago"), `actor`, `operation`, the capture's display name, the destination(s), `route`, `chosen_rank`, and an **undoability verdict**. That last column is the point: the view tells Matt what he can take back and, when he cannot, why, without him pressing anything.

**The verdict is two-tiered, computed by ONE function with a `cheap_only` flag.** The **cheap tier** reads only the corpus and `stat()`: operation type, already-undone, the actor rules, age, `undo.enabled`, and the existence of the archive / restore source. The **expensive tier** reads file bytes: `capture.content_hash`, `targets[].after_hash`, the per-key frontmatter comparison, the append block-and-marker match. `history.list` runs the cheap tier for every row and reports `undoable: true | false | "unknown"`, with `refusal` set only for cheap-tier refusals; **`"unknown"` means the cheap tier passed and no hash was read.** `op.undo` runs both tiers. The split is not fastidiousness: at `limit = 50`, a single-tier `H` would trigger up to ~100 `sha256` reads of vault files on one keystroke (§9 gives `history.list` its own budget). One function, two callers, pinned both ways by test — the cheap tier for both callers, the full predicate for `op.undo --dry-run` (§9).

## 7. The client surface

**One key, one ordered ring.** The client keeps a per-session ring (depth `ui.undo.view_depth`) that interleaves, in real time, view changes and vault operations. A **view entry** holds the previous view snapshot — sort mode, selection, right-pane view, browse stack + path, search query/scope, focused pane, **`pinned_destination`, and `batch_marks`**. A **vault entry** holds `{ action_ids: [...], batch_size: n }` and nothing else — no paths, no hashes; the thin client stores no vault state (10 §1). `u` pops the ring: a view entry is undone locally with **no RPC**; a vault entry calls `op.undo`. `U` redoes symmetrically (a vault redo is `op.undo` addressed at the inverse records). This is not magic — it is what every editor does — and the ambiguity Matt would otherwise face is removed by the toast, which always names the layer and the thing: `undid: sort → Alphabetical`, `undid: pin → areas/health`, `undid: batch mark (12 captures)`, `undid: move → areas/health`. When the session ends the ring dies; vault undo remains reachable through history.

**One `u` undoes a whole batch, all-or-nothing.** Doc 16 defers this decision here, and here it is: a `<leader>ba` over 100 captures pushes **one** vault entry holding 100 `action_ids`, not 100 entries. `op.undo` evaluates **every** member's preconditions first (invariant 1, applied across the group); if any member refuses, **none** is undone and the refusal names the offending member. Exactly one confirmation is shown and it carries the literal count — `undo 100 moves?` — and the reversal emits one inverse `ActionRecord` **per member**, each with its own `context.undoes`, so §5's `undone(X)` recursion and `context.undoes: str | None` are untouched. **Ring depth does not bound the batch**: the entry holds ids, not depth, so `ui.undo.view_depth = 20` never truncates a 100-capture reversal. The alternative — 100 records of which `u` reaches at most 20, one press each — makes the panic case undo exists for the one case it cannot serve.

**The sticky pin and the batch marks are undoable, client-locally.** Doc 16 calls a silently-pinned destination the most dangerous feature in that document, and a pin is closer to Matt's "previous sort" than a browse descent is. `P` then `u` therefore leaves nothing pinned and issues **zero** RPCs (§8), and the same holds for clearing a 100-capture batch mark.

**`u` is bound in the organize pane only, and only while that pane is read-only.** The capture pane is the real capture file's buffer (10 §4) where `u` is Vim's own undo, and shadowing it would be indefensible — so the `undo` / `redo` / `history` rows carry `panes = {"organize"}` and are **not** subject to `ui.capture_pane_keymaps`; that knob may not promote them. But the organize pane is *not* a read-only `nofile` pane in every state: `vim.bo[ui.organize_buf].modifiable = (view == "merge") or editing` (`ui.lua:603-604`). In merge and in integrate-with-editing the pane holds text that `<leader>mc` writes into a real vault note, and a `u` there would fire `op.undo` on an unrelated vault action **while the typed merge text became unrecoverable** — the only data-loss path of its kind in the series. Therefore, per architect ruling R8, these three keys are **view-scoped**: registered through `actions.register_key{ name, default, desc, panes, views, fn }` (the field is `views`, a list of view names — R10; `mode` means the Vim mode in Neovim and is not it) with `views = {"suggestions", "browse", "search", "mru", "history"}`, and **unbound whenever the organize buffer is modifiable**, through the same `bind_gate` / `unbind_gate` mechanism `e` already uses.

`H` opens the history view, a **sixth** right-pane state (03 §3's four became five with the 12 §1 review gate). Adding it as a third hardcoded branch in `render.right_pane` is refused: the dispatch must be a `render.VIEWS[name] = fn` table. **Doc 15 owns `lua/para-organize/ui/render.lua` and lands that registry first as a standalone refactor** (R37); this doc then registers exactly one row, `render.VIEWS["history"]`, and edits nothing else in that file.

**Confirmation: instant, no modal.** Default `ui.undo.confirm = "outside_session"` — an action taken in this session undoes on the keystroke with a toast; an action reached through history from hours ago prompts once with a one-line summary. A modal in front of every undo is backwards: undo *is* the safety net, and making it expensive makes people stop reaching for it. The cost of a mis-press is one keystroke (`U`), because undo is itself undoable. Refusals are the loud path: they surface as an error-level notify carrying the §3 one-liner, and — because they are precondition failures — nothing was touched, so there is nothing to clean up. `"never"` and `"always"` exist for other people's risk tolerance.

**After an undo the UI shows** the restored capture in the left pane (a real buffer on the restored path, re-resolved through `note.get`), regenerated suggestions in the right pane, the recomputed counts line, and the toast. `state.selected` resets to 1; `shown_at` resets so `durations_ms.decision` on the *next* action measures a fresh decision, not one contaminated by the detour.

**Session-state restoration** is what makes undoing a skip actually work — and it is a **core mutation first, a client instruction second.** `op.undo` mutates the **live core `Session`** before it returns: a new `Session.unmark(path)` method removes the path from `processed` / `skipped` and raises `SessionError` when the session is closed. Only then does `result.session` report the client's mirror instruction. Without the core-side half, `session.advance_to_next_unprocessed` walks straight past the capture the toast claims is "literally back in front of him", and the two halves disagree on the next keystroke. The client never infers the instruction:

| Undone action | Client does |
|---|---|
| `skip` in this session | Remove the path from `session.skipped`; re-insert the capture at `index`; set `session.current` to it; reload suggestions. The capture is literally back in front of him. |
| `move` / `archive` / `merge` / `integrate` in this session | Remove from `session.processed`; re-insert at `index`; set `current`; re-`note.get` (the file is back at its original path). |
| Anything from a previous session | `restore: "append"` — the restored note is appended to the **end** of the queue if it matches the session's filters, and the toast says so. Injecting a note from a dead session mid-queue would silently renumber "Capture i of n" under him. |

Restoration requires `processed`/`skipped` in their default **list-of-paths** form. The numeric-aggregate form some readers tolerate carries no paths, so undo refuses the session half with `session: null` and a plain message rather than guessing a position.

## 8. Acceptance tests

1. **Move round trip, bytes on disk.** Move a capture, `organize undo`, assert: the capture file exists at its original path with a sha256 equal to the pre-move file's, its frontmatter has no `project/…` tag and `processing_status` is back to `raw`; the organized copy is gone from the destination and present under the archive at the collision-suffixed path (correct under retire-first: the archive slot is written while the original is still archived); the operation log holds a `move` line, an `archive` line and two `undo` lines; the corpus holds exactly two records, the second with `context.undoes` equal to the first's `id`.
1b. **Retire-first crash interim.** Kill the process between the two steps of a move undo and assert: the organized copy is **gone** from the destination, the note exists **only** under the archive, and **no** live file under `capture/` shares the archived note's `id` or `aliases` — i.e. the doc-06 pipeline has nothing to re-consume. Firing control: the same test on the completed (un-killed) undo finds the capture live and the destination empty.
2. **Undo of undo is redo.** Undo the move, undo the inverse, assert the vault is byte-identical to the post-move state, three records exist, and `undone(A)` is **false** by the §5 recursion.
3. **Changed target refuses, touching nothing.** Merge a capture into a target, append one byte to the target, `organize undo`: exit 1, stderr's first line matches `^ConcurrentModificationError: `, the target's bytes and mtime are unchanged, the capture is still archived, and **no new oplog line and no new ActionRecord were written**.
4. **Append tier 2.** Route-append a capture, edit an unrelated paragraph of the target, undo: the appended block and its marker are gone, the unrelated edit survives verbatim, and the record's `targets[].diff` shows only the excision. With `append_strategy = "restore_only"` the same input refuses with `UndoRefused`.
5. **No restore source, no undo.** With `file_ops.create_backups = false` and a target **over 64 KB** (so `before_text` was not captured), merge then undo: refuses with `UndoRefused: no restore source exists for act_…`, and `organize health` names `file_ops.create_backups` as the reason merge/append/integrate undo is unavailable. **Firing control:** the same configuration with a target **under 64 KB** undoes successfully from `targets[].before_text`.
6. **Batch is all-or-nothing.** A two-destination route batch where the second target was edited since: undo refuses, and the **first** target is byte-unchanged.
6b. **A ≥21-record batch undoes on one press.** `<leader>ba` over 21 captures (one more than `ui.undo.view_depth = 20`, proving depth does not bound it), then one `u`: exactly one confirmation is shown carrying the literal `21`, all 21 captures are back at their capture paths, 21 inverse records exist each with its own `context.undoes`, and `history.list` reports `batch_size: 21` on each. **Firing control / negative half:** edit the destination file of member 14 first, press `u`, and assert **zero** files changed, the refusal names member 14, and no record was written.
6c. **The pin and the batch marks undo locally.** `P` a destination, then `u`: nothing is pinned, the toast reads `undid: pin → areas/health`, and **zero** RPCs were issued (assert against the mock core's call log). Same shape for `x`-marking 12 captures then `u`: `undid: batch mark (12 captures)`, zero RPCs.
7. **Skip returns the capture.** In a headless-nvim session, skip capture 3, press `u`: **core-side**, `Session.unmark` has removed the path and `session.advance_to_next_unprocessed` returns that capture rather than skipping past it; **client-side**, `session.skipped` no longer holds it, `session.current` points at it (1-based), the left pane buffer is its file, and the counts line reads the pre-skip numbers. Assert both halves; a test that checks only the client half passes with the core mutation deleted.
7b. **`Session.unmark` on a closed session.** Undo a skip whose session has been closed: `SessionError` core-side, `session: null` in the result, the vault half still applied, and the toast says the session is gone.
8. **`u` never shadows Vim undo.** In the same session, focus the capture pane, type text, press `u`: the buffer text is reverted by Vim and **no** `op.undo` RPC was issued (assert against the mock core's call log).
8b. **`u` is unbound while the organize buffer is modifiable.** Enter the merge view (and separately, integrate with `editing = true`), assert `vim.fn.maparg("u", "n")` in the organize window is **empty**, type merge text, press `u`, and assert the typed text is reverted by Vim and **no** `op.undo` RPC was issued. **Firing control:** leave the merge view and assert `u` is bound again and does issue `op.undo`. This is the R8 data-loss path; a test that only checks the capture pane (test 8) passes with the view gate deleted.
9. **Learning is rebuilt, not decremented.** Move three captures to the same folder, undo the second, drain the deferred rebuild, assert `learning.json`'s `destinations[dest].count == 2` and `statistics.total_moves == 2`; rebuild twice and assert the two files are **byte-identical**. Assert `op.undo`'s own result carried `learning: { "rebuilt": "scheduled" }` and **no** `records_replayed` / `duration_ms` key.
9b. **The rebuild is backed up and does not over-evict.** Assert a snapshot of the pre-rebuild `learning.json` exists under `<backup_dir>/` after every rebuild, and that a rebuild triggered by one undo reduces the destination count **by at most that record's own contribution** — `apply_decay` hard-deletes past the eviction window, so replaying at each record's own `ts` can otherwise evict associations no undo touched. **Firing control:** a corpus whose oldest records genuinely fall outside the eviction window reports those destinations in `evicted[]` and the assertion is written against `evicted[]`, not against "nothing was evicted".
10. **The undone action stops being a precedent.** After undoing a move, `organize actions query --similar-to "<that capture's text>"` does not return it, while `organize actions export` still emits both lines.
11. **`create_folder` and `consumer:taskwarrior` refuse** with the exact §3 message shapes; the taskwarrior refusal names `~/.task` and the consumer backup dir. **Firing control on the consumer discriminator:** a `consumer:learn` record whose `operation` is `meta_edit` **undoes successfully**, proving the rule is "operation is not `meta_edit`/`tag_edit`" and not "actor starts with `consumer:`".
12. **Machine may not undo a human.** Configure a **non-default** human actor — `[identity] actor = "ada"` — and issue an `op.undo` whose context actor is `auto-organize` against a record with `actor: "ada"`: refuses with `UndoRefused`, the message names `"ada"`, and `learning.json` is byte-unchanged. Written this way, the test **fails if anyone hardcodes a name**. Second half: the same machine actor may not undo a record performed by `consumer:learn` in another run, and **may** undo a record it performed itself in the same run.
12b. **Undone accepts stay in the denominator, and machine undos count against.** Land 10 rank-1 accepts by `auto-organize`, undo N of them with a machine actor, and assert `stats.top_accept_rate` is **never higher** than before — strictly lower for N ≥ 1. **Firing control:** N human undos of the same records leave the denominator intact and the rate unchanged-or-lower, never higher.
12c. **Frontmatter drift refuses the whole action.** `meta_edit` sets `tags` and `status`; a separate writer then adds one tag; `organize undo`: refuses with `UndoRefused: tags changed since act_…`, **`status` is not restored either** (the refusal is whole-action), and the file's bytes and mtime are unchanged. **Firing control:** the same undo with no drift restores both keys and leaves every *other* frontmatter key — including one written by the auto-tagger after the edit — untouched.
12d. **Restoring onto an occupied path.** Two rows, distinct messages, nothing written by either: (a) a **different** note occupies the capture path ⇒ `is occupied by a different note`; (b) a note with the **same id** occupies it ⇒ `is already occupied by a note with this id`. Assert in both cases that **no** `_1`-suffixed file was created and the occupant was not relocated.
13. **v1 corpus is undoable.** A fixture corpus written at `schema_version: 1` with no `undoes` key anywhere: every record reads back with `undoes == None`, the undone set is empty, and a v1 `move` record undoes successfully.
14. **History honesty, and the cheap tier is honest about not knowing.** `organize actions history --json` over a corpus containing one undoable move, one already-undone move and one `create_folder` returns `undoable` values `["unknown", false, false]` and `refusal_kind` values `[null, "UndoRefused", "UndoRefused"]` — the first row is `"unknown"`, not `true`, because the cheap tier read no hashes. Assert **zero** file-content reads occurred during the call (patch the hasher and count). `op.undo --dry-run` on that first row then returns `undoable: true`.
15. **Append undo rewinds the delivery store.** Route-append a capture, undo, assert the doc-06 delivery-store row for that capture no longer reads *delivered*. With the store unreachable, the undo still succeeds on the vault half and `context.partial_failure` **names the store**.
16. **Two spellings of "no age limit" cannot both work.** With `max_age_days = 0`, a 400-day-old record undoes. With `max_age_days = 30`, a 31-day-old record refuses and a **29**-day-old record undoes (the firing control), and a **30**-day-old record undoes — pinning `>` rather than `>=`.

## 9. Test obligations (anti-vacuity)

Binding on the seat that builds this and on its verifier; these are gates, not suggestions.

- **Every refusal predicate in §3 gets a guard-deleted pin.** For each row: delete or invert that one guard in a scratch copy and the corresponding test must **fail**. A refusal test that still passes with its guard removed is proving nothing — and here it would be proving nothing about the exact code path that stands between Matt and data loss. Enumerate them in the test module docstring so a reviewer can count rows against tests. **And each row gets a firing control at an adjacent parameter where the operation must succeed, named per row** (ARCHITECTURE.md:1516-1518) — for `max_age_days`, a record one day inside a `max_age_days = 30` window must undo; for the per-key drift row, an undo with no drift must restore both keys; for the same-id occupancy row, a free capture path must restore; for the consumer discriminator, a `consumer:learn` `meta_edit` must undo. A guard that refuses **everything** passes a guard-deleted test, which is exactly what the firing control exists to catch.
- **Mutation audit before handback.** For each refusal, mutate the predicate three ways — always-true, always-false, and boundary-off-by-one (e.g. hash compare → prefix compare, `>` → `>=` on `max_age_days`, same-id occupancy → any-occupancy) — and record which test caught which mutation. Any mutation caught by nothing is an untested predicate and blocks handback. The audit table must include a row for **each** of the two occupancy branches, the per-key frontmatter comparison, the `frontmatter_after is null` branch, the two machine-actor rules, and the oplog-join ambiguity refusal.
- **Constant assertions are literals.** Assert `"UndoRefused"`, `2` (the schema version), `"restore_or_excise"`, `50` (`ui.undo.history_limit`), **`0` (the `max_age_days` "no limit" spelling) and its boundary (`31` refuses, `30` and `29` undo at `max_age_days = 30`)**, `2` (`scan_months`), `20` (`ui.undo.view_depth`), `"outside_session"` — never the imported module constant, which makes the test agree with any future value of itself.
- **Must-not-be-connected invariants.** Assert positively that: the client issues **no** RPC for a view undo, a pin undo, or a batch-mark undo; a refusal writes **no** corpus line and **no** oplog line; `query`/`export` do **not** filter undone records; `LLM_EDIT_ACTORS` is still exactly `{"claude-integrate"}` after this feature lands; **after N machine undos of machine actions, `stats.top_accept_rate` is never higher than before**; `op.undo`'s result contains **no** `records_replayed` and **no** `duration_ms` key.
- **Both-ways seam pin.** The **cheap tier** must be pinned from both callers (`op.undo` and `history.list`) and the **full predicate** from `op.undo --dry-run`: a table-driven test feeds each §3 scenario and each §3-matrix row to both entry points and asserts identical `kind` and identical message, and asserts that `history.list` reports `"unknown"` — not `true` and not `false` — for every scenario whose only refusal would be expensive-tier. Two predicates that drift is how a history view starts lying.
- **Every key in §6's config block is tested two-sidedly.** One test per key — `undo.enabled`, `undo.scan_months`, `undo.max_age_days`, `undo.rebuild_learning`, `undo.append_strategy`, and the nvim `ui.undo.confirm` (all three values), `ui.undo.history_limit`, `ui.undo.view_depth` — asserting behaviour A at the default and a **different** behaviour B at a non-default. The Lua half rides on **14 §10.11's Lua mirror gate and Lua honored-key gate** (config.lua SCHEMA leaf ⇒ reader; default ⇒ behaviour A, non-default ⇒ behaviour B ≠ A), which doc 14 builds before any key here ships; this doc adds no bespoke Lua harness. Eight rows, eight tests, countable by a reviewer.
- **Never-delete guard unchanged.** Assert the AST guard's `allowed` set still names exactly its sanctioned functions after the undo path lands. Undo **reuses** the verified relocator and never adds a fourth deleter — and `src/organize_core/fileops.py` is **doc 18's file** under R37, so any rename/re-documentation of that relocator is a request to that seat, not an edit from this one.
- **Torn-write and crash tests** for the inverse record, matching 12 §3's obligation: an interrupted undo leaves no partial JSONL line, and a crash between the vault write and the corpus append is detectable (the file moved, no `undoes` marker) — assert the next `undo` of the same action refuses on state rather than silently double-applying.
- **Perf budgets (09 §4).** `op.undo` must return within the 50 ms UI-response budget for the vault half **including the corpus mark and the rebuild enqueue** — the rebuild itself is deferred (§4) and is measured separately, marked `-m slow`. Assert that **a concurrent `suggest.for_note` completes during the rebuild's compute phase**, which is the observable consequence of computing off-lock; the write lock is taken only for the final swap and `learn.save`. `history.list` gets its own budget: **< 50 ms at `limit = 50`**, with an assertion that the call performed **zero** file-content reads (the cheap tier), since `H` is a keystroke and a single-tier implementation would trigger ~100 `sha256` reads of vault files.
